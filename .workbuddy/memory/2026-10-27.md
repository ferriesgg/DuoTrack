# 2026-10-27

## DuoTrack 代码评审（架构 + 代码质量）

项目概况：.NET 8 键鼠跨机控制工具。三项目 + 五测试程序，生产代码约 3750 行、测试约 710 行。

分层：
- `src/DuoTrack.Protocol` — 线格式 `InputPacket`（13B）/ `RelayWire`（30B 单帧、19+13n 批量、9B ping）
- `src/DuoTrack.Relay` — Minimal API 单文件 `Program.cs`，SQLite，配对码，WS 转发
- `src/DuoTrack.Client` — WPF + Win32 钩子，独立 STA 输入线程，LAN mTLS 直连

评审结论要点：
- 优点：零编译告警；协议紧凑且向后兼容（subprotocol 协商）；测试跑真实 TLS/真实 socket，覆盖 2048 帧顺序、伪造证书拒绝、配对缓存并发失效；私钥 DPAPI 保护、公钥固定（SPKI base64 比对）、自注入回环过滤（ExtraInfo tag）。
- 主要问题：
  1. Relay 未启用 `UseForwardedHeaders`，在 Caddy 后 `RemoteIpAddress` 全是容器 IP → 限流退化为全局单桶。
  2. `SessionStore` / `challenges` 无过期清理，客户端每 3s 重连会不断新建 session token → 服务端内存泄漏。
  3. `MainWindow.xaml.cs` 544 行 God Object：UI + 跨屏状态机 + 注入 + 设置混在一起。
  4. 大量 `Async` 后缀方法实为同步返回 `Task.CompletedTask`；`async void` 事件处理器。
  5. 无 .sln / .editorconfig / CI；测试是 Console + throw，非 xunit。
  6. README 仍写需要开放 80 端口，但 compose/Caddyfile 已改用 TLS-ALPN（文档过时）。
  7. Dockerfile 用 .NET 8 非 root 用户 + 具名卷 `/data`，权限是否可写需实测。
- 构建注意：本机 `dotnet restore` 报 `Value cannot be null (Parameter 'path1')`（NuGet 目标），属环境问题；改用 `dotnet build --no-restore` 可正常编译，0 警告 0 错误。

待办/观察：工作区有 16 个文件未提交（含新增 ScrollPlayback、RelayTests），提交粒度较粗。

## 双指滚动卡顿 — 根因定位

结论：**滚动增量被多处合流成少量大 delta 一次性注入，时间分布被破坏；唯一的平滑补偿 `ScrollPlayback` 在局域网直连路径被显式关闭。**

证据链：
1. `TouchpadTests:84` 断言 — 10,000 个滚动增量经 `InputDispatchQueue` 后变成 1 个 delta=10000 的包（作者自己写的预期行为）。
2. 实测 `TransportTests` 输出 — `4,000 precision scroll deltas sent as 81 LAN packets`（平均 delta≈49）。
3. `MainWindow.cs:404` — `if (...MouseWheel && _scrollPlayback.Enabled && !direct)`：`!direct` 使 LAN 直连（默认优先路径）跳过 ScrollPlayback。UI 开关名就叫"公网滚动平滑"，确认只覆盖中继。
4. `InputDispatchQueue` 复用 `InputPacketQueue`，接收端同样会合并相邻滚轮（TryMerge：同 peer/同 direct/同 Type/同 Value2 轴/同 Flags/同符号即合并，保总量但丢时间分布）。
5. `ScrollPlaybackBuffer._steps = 2` + 8ms 时钟 → 即便在中继模式，一个大 delta 也只拆成 2 片、16ms 播完，平滑能力有限。
6. `InputDispatchQueue.Drain` — 每轮 `count<64 && budget<4ms`，超时即重排一次 `BeginInvoke(DispatcherPriority.Input)` 调度往返，注入节奏不均。

加剧项：
- 发送端 `SendLoopAsync` 一次最多批量写 64 帧；接收端 `ReadPeerAsync` tight-loop 逐帧读 14B 并立即 Enqueue → 一批包在几毫秒内全部入队并合并，突发性被放大。
- `PeerLink.WriteAsync` / `SendRelayAsync` 每帧都新建 `CancellationTokenSource` + `CancelAfter`，高频滚动下开销可观，会拖慢 SendLoop 并诱发积累。
- **滚轮实际走的是 WH_MOUSE_LL 钩子，不是 README 描述的 Win32 输入窗口**：`InputHookManager.MouseHook` 在 `_forwarding` 时对 WM_MOUSEWHEEL 转发后 `return 1` 吞掉消息，所以 `RemoteInputWindow.WindowMessage` 的滚轮分支（96-105 行）是死代码 → README 承诺的"由 Windows 处理加速度/惯性"未生效。
- `InputHookManager._mouseAnchor` 转发期间从不更新（无 SetCursorPos 回中），本机光标会漂到边缘；且 `SetCursorPos` 产生的移动 ExtraInfo=0，不被钩子过滤，会污染输入流。

修复方向（按优先级）：
1. 去掉 `MainWindow.cs:404` 的 `&& !direct`，让 LAN 也走播放缓冲（1 行，最低风险）。
2. `ScrollPlaybackBuffer` 按目标时长（60-100ms）动态算步数，别固定 2 步。
3. 接收端改为固定周期匀速出队（~8ms），而非"尽快出队 + 合流"。
4. 修 RemoteInputWindow 死路径 + `_mouseAnchor` 回中。

注意：合流本身是为"保滚动距离不丢精度"，不能简单删除。

环境备注：`tests/TransportTests` 在本沙箱构建稳定失败（MSBuild 子节点 2 过早退出），但 `bin/` 下已有 exe 可直接运行拿基线。
